# HFMG AI Help Desk — API Specification

**Framework:** FastAPI
**Base path:** `/api/v1`
**Format:** JSON (`application/json`), UTF-8
**Auth:** Bearer JWT (`Authorization: Bearer <token>`), except where noted

This document is the source-of-truth contract; the live OpenAPI schema generated by FastAPI at `/api/v1/openapi.json` (and interactive docs at `/docs`) must stay in sync with it during implementation.

## 1. Conventions

### 1.1 Envelope

Single resources are returned as a plain JSON object. Collections are returned wrapped for pagination:

```json
{
  "items": [ ... ],
  "page": 1,
  "page_size": 25,
  "total": 132,
  "total_pages": 6
}
```

### 1.2 Errors

Standard error shape for all non-2xx responses:

```json
{
  "error": {
    "code": "TICKET_NOT_FOUND",
    "message": "Ticket HFMG-2026-000482 was not found.",
    "details": null
  }
}
```

| HTTP Status | Meaning |
|---|---|
| 400 | Validation error (also used for Pydantic request validation failures, with `details` populated with field errors) |
| 401 | Missing/invalid/expired auth token |
| 403 | Authenticated but not authorized for this action |
| 404 | Resource not found |
| 409 | Conflict (e.g., duplicate category name) |
| 422 | Semantically invalid request (e.g., invalid status transition) |
| 429 | Rate limited |
| 500 | Unhandled server error |
| 502/504 | Upstream dependency (AI provider, email provider) failure surfaced from a synchronous admin-triggered action |

### 1.3 Pagination, filtering, sorting

List endpoints accept:
- `page` (default `1`), `page_size` (default `25`, max `100`)
- `sort` — e.g. `sort=-created_at` (`-` prefix = descending); whitelisted fields per endpoint
- Resource-specific filters as query params (documented per endpoint)

### 1.4 Versioning

URI-versioned (`/api/v1/...`). Breaking changes ship as `/api/v2`; additive/backward-compatible changes (new optional fields, new endpoints) ship within `v1`.

### 1.5 Idempotency

State-changing `POST` endpoints that may be retried by a client (notably the Twilio webhook) accept an `Idempotency-Key` header or rely on a natural external key (`twilio_call_sid`) to avoid duplicate processing.

## 2. Authentication

### `POST /api/v1/auth/login`
Authenticate with email/password (internal accounts). If HFMG adopts SSO/OIDC, this is replaced/supplemented by `/api/v1/auth/oidc/callback`.

**Auth:** none

Request:
```json
{ "email": "jsmith@hfmg.net", "password": "..." }
```

Response `200`:
```json
{
  "access_token": "eyJ...",
  "token_type": "bearer",
  "expires_in": 900,
  "user": { "id": "uuid", "full_name": "Jane Smith", "email": "jsmith@hfmg.net", "role": "AGENT" }
}
```
Refresh token is set as an httpOnly, secure, `SameSite=Strict` cookie — never returned in the JSON body.

### `POST /api/v1/auth/refresh`
Exchanges the refresh cookie for a new access token. **Auth:** refresh cookie required.

### `POST /api/v1/auth/logout`
Revokes the refresh token/cookie. **Auth:** required.

### `GET /api/v1/auth/me`
Returns the current authenticated user. **Auth:** required.

## 3. Tickets

### `POST /api/v1/tickets`
Create a new ticket. Used by the web intake form; also the target of the future Twilio pipeline internally (via the domain service, not necessarily this HTTP route — see `ARCHITECTURE.md` §5.5).

**Auth:** required (`REQUESTER`, `AGENT`, or `ADMIN`)

Request:
```json
{
  "caller_name": "Maria Lopez",
  "phone_number": "+15551234567",
  "email": "mlopez@hfmg.net",
  "category_id": "b3f1...uuid",
  "priority": "HIGH",
  "description": "EHR login fails with 'session expired' on all exam room workstations since 8am."
}
```

Validation:
- `caller_name`: required, 1–200 chars.
- `phone_number`: required, E.164-normalizable.
- `email`: optional, valid email format.
- `category_id`: required, must reference an active category.
- `priority`: optional; defaults to the category's `default_priority` or `MEDIUM` if omitted.
- `description`: required, 1–10,000 chars.

Response `201`:
```json
{
  "id": "8f14...uuid",
  "ticket_number": "HFMG-2026-000482",
  "caller_name": "Maria Lopez",
  "phone_number": "+15551234567",
  "email": "mlopez@hfmg.net",
  "category": { "id": "b3f1...uuid", "name": "EHR / Clinical Systems" },
  "priority": "HIGH",
  "description": "EHR login fails with 'session expired' on all exam room workstations since 8am.",
  "ai_summary": null,
  "ai_summary_status": "PENDING",
  "status": "NEW",
  "source": "WEB",
  "assigned_agent": null,
  "due_at": "2026-09-19T14:00:00Z",
  "created_at": "2026-09-18T14:00:00Z",
  "updated_at": "2026-09-18T14:00:00Z"
}
```

Side effects (async, non-blocking): enqueues AI summarization job and `TICKET_CREATED` notification job to `helpdesk@hfmg.net`.

### `GET /api/v1/tickets`
List/search tickets.

**Auth:** required. `REQUESTER` role is scoped to tickets where `requester_user_id == self` or `email == self.email`; `AGENT`/`ADMIN` see all. (Not yet enforced — no auth exists in the MVP; every ticket is visible to any caller.)

Query params — **✅ `status`, `category_id`, `priority`, `source`, `q` are all implemented today**; `assigned_agent_id`/`created_after`/`created_before`/`sort` are target-only (⬜ not built — no `assigned_agent_id` column exists, and list order is always `created_at desc`):
| Param | Status | Notes |
|---|---|---|
| `status` | ✅ | repeatable, e.g. `?status=NEW&status=OPEN` |
| `priority` | ✅ | single value only today, not yet repeatable |
| `category_id` | ✅ | filter by category |
| `source` | ✅ | `WEB` / `PHONE` / `EMAIL` / `WALK_IN` |
| `q` | ✅ | matches via `ILIKE` over `caller_name`/`ticket_number`/`description`/`ai_summary` — **not** the full-text (`to_tsvector`) search this section originally implied; `ix_tickets_fts` does not exist in the database (see §0) |
| `assigned_agent_id` | ⬜ | no `assigned_agent_id` column in the MVP schema |
| `created_after`, `created_before` | ⬜ | not built |
| `sort` | ⬜ | not built — always `created_at desc` |

Response `200`: paginated envelope of ticket summaries (lighter shape than detail — excludes `description`/`ai_summary` body to keep list payloads small; full text available via `GET /tickets/{id}`). Both the list and detail shapes include `source` (`WEB`/`PHONE`/`EMAIL`/`WALK_IN`) as of this update — it was present in the `tickets` table since Phase 2 but not serialized in either response until now.

### `GET /api/v1/tickets/{ticket_id}`
Full ticket detail, including `description`, `ai_summary`, `ai_summary_status`.

**Auth:** required; same scoping rule as list.

### `PATCH /api/v1/tickets/{ticket_id}`
Partial update — editable fields: `caller_name`, `phone_number`, `email`, `category_id`, `priority`, `description`.

**Auth:** `AGENT`/`ADMIN` only (requesters cannot edit after submission; they add comments instead).

Response `200`: updated ticket. Each field change is written to `audit_log`.

### `POST /api/v1/tickets/{ticket_id}/status`
Explicit status transition endpoint (kept separate from generic `PATCH` because transitions carry business rules — e.g., `RESOLVED` requires at least one comment, `CLOSED` sets `closed_at`).

**Auth:** `AGENT`/`ADMIN`

Request:
```json
{ "status": "RESOLVED", "resolution_note": "Reset session cache on affected workstations." }
```

Response `200`: updated ticket. Enqueues `TICKET_STATUS_CHANGED` (and `TICKET_RESOLVED` when applicable) notification.

Invalid transitions (e.g., `CLOSED` → `NEW`) return `422` with `code: "INVALID_STATUS_TRANSITION"`.

### `POST /api/v1/tickets/{ticket_id}/assign`
Assign/reassign a ticket to an agent.

**Auth:** `AGENT`/`ADMIN`

Request:
```json
{ "assigned_agent_id": "uuid" }
```

Response `200`: updated ticket. Enqueues `TICKET_ASSIGNED` notification.

### `POST /api/v1/tickets/{ticket_id}/regenerate-summary`
**✅ Implemented.** Manually re-trigger AI summarization (e.g., after a description edit, or if the first attempt failed).

**Auth:** `AGENT`/`ADMIN` (not yet enforced — no auth exists in the MVP)

Response `202`:
```json
{ "ai_summary_status": "PENDING" }
```

Response `409` if `ENABLE_AI_SUMMARY` is off deployment-wide — there is nothing a regenerate call could ever complete into, so this rejects rather than leaving the ticket stuck in `PENDING` forever.

Response `404` if the ticket doesn't exist.

### `GET /api/v1/tickets/{ticket_id}/comments`
List comments on a ticket (internal notes + requester-visible updates, filtered by role — requesters never see `is_internal=true` comments).

### `POST /api/v1/tickets/{ticket_id}/comments`
Add a comment.

**Auth:** required.

Request:
```json
{ "body": "Escalated to network team.", "is_internal": true }
```
`is_internal` forced to `false` for `REQUESTER`-authored comments regardless of payload.

### `POST /api/v1/tickets/{ticket_id}/attachments`
Upload an attachment (`multipart/form-data`). Backend streams the file to object storage and writes `ticket_attachments` metadata.

**Auth:** required.

### `GET /api/v1/tickets/{ticket_id}/attachments/{attachment_id}`
Returns a short-lived signed download URL rather than the file bytes directly.

## 8. Webhooks — Twilio Voice Integration (Phase 2, implemented)

These endpoints back the AI voice agent. Full design: [TWILIO_ARCHITECTURE.md](TWILIO_ARCHITECTURE.md), [CALL_FLOW.md](CALL_FLOW.md), [VOICE_AGENT_DESIGN.md](VOICE_AGENT_DESIGN.md).

**Auth for all four:** Twilio request-signature validation (`X-Twilio-Signature`, verified against the configured auth token) — never JWT. Unsigned or tampered requests get `403`.

**Content type:** requests are Twilio's form-encoded payloads; responses are TwiML (`application/xml`), except the status callback which returns `204`.

### `POST /api/v1/webhooks/twilio/voice`
Turn 0. Creates the call session (keyed by `CallSid`, idempotent on retry), returns the greeting wrapped in a `<Gather input="speech">`.

Request fields: `CallSid`, `From` (caller ID — captured silently as the callback number when usable), `To`.

### `POST /api/v1/webhooks/twilio/voice/gather`
Turns 1..N. Receives the caller's transcribed speech, advances the conversation state machine, and returns the next prompt or the final hangup.

Request fields: `CallSid`, `SpeechResult`, `Confidence`.

Ticket creation happens inside this endpoint when collection completes, calling the same `TicketService.create_ticket()` the web form uses with `source: "PHONE"`, then dispatching the AI summary and `helpdesk@hfmg.net` notification as background tasks. The caller hears their ticket number without waiting on the summary.

### `POST /api/v1/webhooks/twilio/voice/status`
Call lifecycle callback. Marks the session ended. If the caller hung up after describing their problem but before intake finished, salvages a ticket flagged `INCOMPLETE VOICE INTAKE` rather than losing the issue. Returns `204`.

Request fields: `CallSid`, `CallStatus`.

### `POST /api/v1/webhooks/twilio/voice/fallback`
Invoked by Twilio when the primary webhook errors or times out. Creates an escalation ticket and plays an apology with a callback promise instead of a Twilio error tone.

### Note on the earlier sketch
An earlier draft of this section specified a single `/call-completed` endpoint that recorded the call and transcribed it afterward. That was replaced by the multi-turn `<Gather>` design above, which collects structured data conversationally instead of post-processing a recording — and avoids call recording entirely, which carries consent requirements (`TWILIO_ARCHITECTURE.md` §9).

## 9. Health & Ops

### `GET /api/v1/health`
Liveness check (no auth). Returns `200 {"status": "ok"}`.

### `GET /api/v1/health/ready`
**✅ Implemented.** Readiness check (no auth) — verifies DB connectivity via a real `SELECT 1`. Returns `200 {"status": "ok"}` or `503` with an error detail if the database is unreachable. There is no worker queue to check (`BackgroundTasks` only, per the MVP scope decision) — DB reachability is this process's only real dependency at request time.

### `GET /api/v1/health/dependencies`
**✅ Implemented, new.** OpenAI/Twilio/Database/Email status strip backing `DESIGN.md` §6.1's System Status Bar. No auth.

Response `200`:
```json
{
  "openai": { "status": "operational", "checked_at": "2026-09-20T08:08:21.447062Z" },
  "twilio": { "status": "down", "checked_at": "2026-09-20T08:08:21.447070Z" },
  "database": { "status": "operational", "checked_at": "2026-09-20T08:08:21.509769Z" },
  "email": { "status": "down", "checked_at": "2026-09-20T08:08:21.509784Z" }
}
```

`status` is one of `operational` / `degraded` / `down` / `unknown` (`degraded` is reserved in the schema but never emitted today — no latency-based signal is measured yet, see `REMAINING_PRODUCT_DECISIONS.md`). Each dependency's check is cached in-process for 30 seconds so this endpoint never triggers a live OpenAI/Twilio/SendGrid call on every dashboard poll. OpenAI and Email checks are real reachability probes (a cheap authenticated `GET`, no email sent, no summary generated); Twilio's check is configuration-only (`TWILIO_AUTH_TOKEN` set or not) because a real call would need `TWILIO_ACCOUNT_SID`, which isn't a configured setting anywhere in this codebase — see `DOCS_GAP_REPORT.md`.

## 11. Settings

### `GET /api/v1/settings/status`
**✅ Implemented, new.** Read-only configuration visibility (`DESIGN.md` §12). No auth. **There is no write path, and none will be added until Phase 3 authentication ships** — this is a security property, not a missing feature.

Response `200`:
```json
{
  "openai": { "configured": true, "status": "operational", "masked_key": "sk-...a1b2", "detail": "Model: gpt-5-nano", "last_verified": "2026-09-20T08:08:21Z" },
  "twilio": { "configured": false, "status": "down", "masked_key": null, "detail": null, "last_verified": "2026-09-20T08:08:21Z" },
  "email": { "configured": true, "status": "operational", "masked_key": "SG....wxyz", "detail": "From reminder@hfmg.net to helpdesk@hfmg.net", "last_verified": "2026-09-20T08:08:21Z" },
  "database": { "configured": true, "status": "operational", "masked_key": null, "detail": "PostgreSQL", "last_verified": "2026-09-20T08:08:21Z" },
  "environment": { "environment": "development", "enable_ai_summary": false, "enable_email_notifications": true }
}
```

Every secret is masked (first 3 + last 4 characters, e.g. `sk-...a1b2`) or `null` if unconfigured — the raw value never leaves `app/core/config.py`. Reuses the same cached checks as `/health/dependencies`, so `status`/`last_verified` never drift between the two endpoints.

## 12. Analytics

All eight endpoints are **✅ implemented, new** — none existed before this change; `OPERATIONS_RUNBOOK.md` §3.3's escalation SQL was previously ad hoc only. Every chart endpoint accepts `?days=` (1–365, default 30) and pre-aggregates server-side (no endpoint returns raw rows for client-side aggregation, per `DESIGN.md` §10).

| Endpoint | Response shape |
|---|---|
| `GET /analytics/kpis` | `{open_tickets, tickets_today, calls_today, escalations, ai_resolution_rate}`, each `{status: "ready"\|"blocked", value, blocked_reason}` |
| `GET /analytics/recent-activity` | `{items: [{type: "ticket_created", occurred_at, ticket_id, ticket_number, caller_name, category, priority, status}]}` — `?limit=` (1–50, default 10). Ticket-derived events only; call events aren't merged in yet (see `WORK_LOG.md`) |
| `GET /analytics/tickets-by-category` | `{items: [{category, count}]}`, ordered by count desc |
| `GET /analytics/tickets-by-priority` | `{items: [{priority, count}]}`, zero-filled for all 4 priorities |
| `GET /analytics/tickets-by-source` | `{items: [{source, count}]}`, zero-filled for all 4 sources |
| `GET /analytics/calls-by-day` | `{items: [{date, count}]}`, zero-filled for every day in the window |
| `GET /analytics/escalation-rate` | `{total_terminal_calls, escalated_calls, rate_percent}` — see the definition note below |
| `GET /analytics/ai-summary-usage` | `{items: [{status, count, percentage}]}`, bucketed by `ai_summary_status` |

**`ai_resolution_rate` is deliberately a blocked field** (`{"status": "blocked", "value": null, "blocked_reason": "..."}`), not a number — `DESIGN.md` §20 lists three non-equivalent candidate definitions and none has been chosen. See `REMAINING_PRODUCT_DECISIONS.md`.

**`calls_today`/`escalations`** use a disclosed, reasonable-default definition (day-scoped, matching their KPI-row siblings) that wasn't fully pinned down in `WIREFRAMES.md`/`DESIGN.md` — flagged in `REMAINING_PRODUCT_DECISIONS.md` for confirmation, not silently assumed.

**Escalation rate's definition** (also disclosed, not confirmed by product): `escalated_calls / calls that reached a terminal state (COMPLETED, ESCALATED, ABANDONED)` in the window. In-progress calls are excluded since they haven't reached an outcome yet.

## 13. Voice Calls (read)

**✅ Implemented, new.** Read-only access to `voice_call_sessions` (`DATABASE_DESIGN.md` §3.8) for the Voice Operations Center (`WIREFRAMES.md` §5). No write endpoints — all conversation-state writes remain internal to the Twilio webhooks in §8.

### `GET /api/v1/voice-calls`
Paginated list, same envelope shape as `GET /tickets`. Query params: `page`, `page_size`, `state` (one of the 11 `voice_call_state_enum` values — see the correction in `CALL_FLOW.md`), `escalated` (bool). Each item denormalizes `caller_name`/`category`/`priority` out of the `collected` JSONB so clients don't need to parse it just to render a table column.

### `GET /api/v1/voice-calls/summary`
`{active, completed, escalated, abandoned}` counts. `active` = any non-terminal state. **Route order matters:** registered before `/{call_id}` so `"summary"` is never parsed as a UUID.

### `GET /api/v1/voice-calls/{call_id}`
Full detail: everything in the list item plus `to_number`, `misunderstanding_count`, `email_attempt_count`, the raw `collected` dict, and the full `turns` transcript array. `404` if the call doesn't exist.

## 15. Rate Limiting

Applied per-IP and per-user at the reverse proxy / API gateway layer:
- `POST /api/v1/tickets`: 20/hour per IP (public-ish intake form) to limit abuse.
- `POST /api/v1/auth/login`: 10/15min per IP (brute-force protection).
- `POST /api/v1/webhooks/twilio/*`: exempted from per-IP limits (Twilio's IPs), protected instead by signature validation.

Exceeding a limit returns `429` with a `Retry-After` header.
